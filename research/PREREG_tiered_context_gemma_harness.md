# Pre-registration: monolithic vs tiered repository context on the Gemma 4 agent harness

> **Terms used below** (editorial note added 2026-11-14; the registered text is unchanged so its history stays verifiable).
> No-context baseline = C0. Monolithic context, the whole context file in the prompt = C1. Tiered context, an always-on
> index in the prompt with sections loaded on demand = C2. Tiered context with tiers assigned automatically = C3.
> Cost hypothesis, tiered uses fewer tokens than monolithic = H1. Quality hypothesis, tiered resolves no fewer tasks than
> monolithic within a margin (delta) = H2. Tiered resolves no fewer tasks than no context = H3. Automatic tiering matches
> manual tiering = H4.

Recorded 2026-11-14 10:01 MT before any run of conditions C1 or C2 (first design, withdrawn; see Amendment 1). This applies
research/RESEARCH_PLAN.md (design v1, 2026-09-04) to a real multi-step agent with real test grading, the run that
research/STATUS.md lists as missing. It is separate from the Agent Track leaderboard plan and uses no leaderboard slot.

## Question and hypotheses (from RESEARCH_PLAN.md section 2)

- H1 (cost): tiered context (C2) uses fewer total tokens per task than monolithic context (C1).
- H2 (quality, non-inferiority): C2's resolved rate is not worse than C1's by more than delta.
- H3: C2's resolved rate is not worse than no context (C0) by more than delta.
- H4 (automatic tiering, C3) is deferred to a later amendment.

## Conditions (one change each from C0; agent, model, budgets, tools and tasks held constant)

| Cond | Arm | Context |
|---|---|---|
| C0 | benchmark/gemma_agent/submission_v81_noskill | none (official sample prompt) |
| C1 | benchmark/gemma_agent/submission_c1_mono | all four repository context files appended to the system prompt |
| C2 | benchmark/gemma_agent/submission_c2_tiered | an always-on index in the system prompt; each file is a skill loaded on demand with load_skill |

Context content (condition A2): one file per repository, generated by research/c1c2/make_context.py from the
snapshot alone (package layout, each module's first docstring line and top-level public names, test layout, pytest
settings copied from the repository's own config). Commits: fastapi ee22a4b, httpx 4acf5c2, requests 6f205ff, rich
fc41075 (research/c1c2/context/). Same-text control: each file appears verbatim in C1 and in C2's skills
(checked by the build). Deviation noted: the repositories' own contributing docs were too thin for fastapi (33
words) and absent for httpx, so the developer-file condition was replaced by a generated file, ETH's other
condition. Model: gemma-4-31b-it-qat-w4a16-ct; tasks: all 129 published tasks; budgets: eval_config.yaml of C0.

## Mechanism gate (checked in traces before any outcome is analysed)

C1: the system instruction in each trace contains all four context files. C2: in at least 80 percent of tasks a
load_skill call names the skill of the task's repository. If a gate fails, the condition is reported as not
implemented and its outcomes are not used for H1 to H3.

## Outcomes and statistics (RESEARCH_PLAN.md section 6)

- Tokens: total_prompt_tokens plus total_completion_tokens per task (trace final_metrics). H1: paired Wilcoxon
  signed-rank, C2 vs C1, one-sided.
- Resolution: H2 and H3 by a paired bootstrap (10,000 resamples) one-sided 95 percent lower bound of the
  difference in resolved rate (C2 minus C1, C2 minus C0) compared with minus delta; exact McNemar reported.
- delta = 0.05 (5 points). Deviation from the plan's 2 points, declared: with the measured discordance of 8 in 129
  paired tasks, 2 points needs about 960 paired runs; one run of 129 detects about 5.4 points at 80 percent power,
  three runs about 3.1 points. Achieved power is reported.
- alpha = 0.05, Holm correction across H1, H2, H3. Effect sizes with intervals and a resolved-rate versus tokens
  (Pareto) plot are reported.
- Repeats: k = 3. Run 1 now (C1 and C2 fresh; C0 from the existing 129-task run of the same arm and harness,
  benchmark/gemma_agent/selftest_results/selftest129_v81_noskill.csv, declared). Runs 2 and 3 after the GPU
  quota resets of 2026-11-21 and 2026-11-28, with fresh C0, C1 and C2. Results stay labelled preliminary until
  all three runs are in; nulls are reported as not detected.

## Amendment 1 (recorded 2026-11-14 11:27 MT, before any outcome of a valid run)

Withdrawn first design (runs launched 10:02 MT). Review found two validity problems before results: (1) C1 put all
four repositories' files in every prompt, so C2 saved tokens only by omitting other repositories' files, a routing
effect rather than tiering; ETH's monolithic condition is the context file of the repository being worked on.
(2) C2 loaded whole files and its prompt forced a first load_skill call that C1 lacked. The C1 run was stopped. The
C2 run completed with 0 tool calls on all 129 tasks: each SKILL.md description contained an unquoted ": ", the
harness rejected the frontmatter as invalid YAML, and the agent never compiled. Neither run is used.
Validator change: skill frontmatter is now parsed with yaml.safe_load, as the harness does
(benchmark/gemma_agent/validate_submission.py); it rejects the withdrawn arm and passes all current arms.

Corrected design, replacing the conditions table above:
- Per-repository arms, routed by task: each task runs with its own repository's arm.
  C1 = benchmark/gemma_agent/context_study/monolithic/<repo>: that repository's whole file in the system prompt.
  C2 = benchmark/gemma_agent/context_study/tiered/<repo>: the always-on part (header, tests, documentation
  examples, and an index of the package-layout sections) in the system prompt; each layout section, grouped by
  directory, is a skill loaded on demand. Sections per repository: fastapi 6, httpx 2, rich 2, requests 1.
- Built by research/tiered_context_gemma/build_arms.py from the files of research/tiered_context_gemma/make_context.py.
  Same-text control (asserted by the build): always-on part plus all sections equal the C1 file exactly; the index
  is the only added text. Both prompts open with the same sentence; C2 adds one sentence saying sections are loaded
  with load_skill when needed. No forced first call.
- H1 primary measure, as in RESEARCH_PLAN.md: prompt tokens per model call (total_prompt_tokens divided by
  model calls, per task), C2 vs C1, paired Wilcoxon, one-sided. Secondary: total tokens per task.
- Mechanism gate: C1 traces contain the whole file; C2 traces contain the always-on part, and the share of tasks
  with at least one load_skill call is reported (no threshold: loading on demand may legitimately be rare).
- H2, H3, delta, alpha, Holm, repeats and labelling as registered above. Run 1: C1 and C2 fresh on 129 tasks; C0
  from the existing 129-task run, as declared.

## Amendment 2 (recorded 2026-11-14 12:18 MT, before any outcome of runs cck-ctx-monolithic-129 or cck-ctx-tiered-129)

Analysis rules fixed before the data, from a validity review:
1. Tool overhead of tiering. The tiered arm declares skills, so the harness adds skill-loading tools, and possibly a
   skill list, to every call. From the traces, the tiered arm's always-on prompt cost is measured as its prompt tokens
   on the first model call minus the monolithic arm's, per task. It is reported beside the H1 result. H1 is tested on
   the measured totals, which include this overhead.
2. Largest possible saving. Per repository, the words a tiered prompt can leave out (the package-layout sections):
   fastapi 286, httpx 246, requests 158, rich 523 (whole files 362, 264, 200, 555). Reported beside the measured saving,
   so a null on H1 can be read against what was achievable.
3. How often sections load. The share of tasks with at least one load_skill call, per repository. If it is under
   20 percent, the tiered arm is described as "less context" rather than "context on demand".
4. Results per repository as well as pooled, because tiering has 1 section for requests, 2 for httpx and rich, and
   6 for fastapi.
5. H3 in run 1 uses the no-context run of 12 to 13 November (different day and machine). Run 1's H3 is reported as
   secondary; the primary H3 test uses the fresh no-context runs of runs 2 and 3.
6. The no-context arm is also stored as benchmark/gemma_agent/context_study/none/all_repositories, an exact copy of
   submission_v81_noskill (same files and checksums).
Not confounds, noted as scope: one model (31B) and small generated files. No claim is made about the size of
developer-written context files elsewhere.

## Related registration: model-agnostic retrieval on SWE-bench Lite (recorded 2026-11-14 15:26 MT, before any result)

To test the writeup's retrieval findings on a standard, model-agnostic benchmark. Queries: the problem statements of
SWE-bench Lite's 300 test tasks (princeton-nlp/SWE-bench_Lite, 12 Python repositories), first 4,000 characters.
Repository: each task's base_commit. Target: the 8-line chunks overlapping the lines its gold patch changes, in
existing non-test .py files. Retrievers and code: the committed BM25 and dense retriever (bge-small-en-v1.5), k = 6, as in
the task-grounded run (research/PREREG_20day_agent_plan.md amendment 19).
Conditions: (1) coverage: dense at full coverage and at 25 percent of chunks, BM25 over all chunks;
(2) chunk length: 8-line chunks vs 400-word chunks at full coverage, dense whole-chunk vs best in-window segment.
Primary: BM25 vs dense at full coverage (paired, exact McNemar, bootstrap interval); dense full vs dense 25 percent.
Secondary: the chunk-length conditions. Predictions, from the writeup: dense at 25 percent falls well below dense at
full coverage while BM25 is unchanged; with 400-word chunks, best-segment scoring raises dense. Nulls are reported as
not detected. CPU only; a 3-task smoke run first. Tasks whose gold patch edits no existing non-test .py file are excluded
and counted.

### SWE-bench Lite retrieval, first shard result: django (recorded 2026-11-14 21:04 MT; preliminary until all shards finish)

114 django tasks, none excluded; hit at k = 6 on the 8-line chunks the gold patch changes.
Coverage (primary): dense full 0.342 [0.263, 0.439] vs dense at 25 percent 0.210 [0.140, 0.289]; 21 vs 6 discordant,
exact McNemar p = 0.006; BM25, which always searches everything, 0.228. The coverage prediction holds on real issues.
BM25 vs dense at full coverage (primary): 0.228 vs 0.342; 10 vs 23 discordant, p = 0.035. On real issue text dense leads,
unlike the docstring questions, where the two were equivalent at full coverage.
Chunk length (secondary): with 400-word chunks, dense whole-chunk 0.430 and best-segment 0.465 (8 vs 4 discordant,
p = 0.39, same direction as the writeup, not detected); BM25 0.482. Longer chunks raised both retrievers here, but each
400-word chunk returns far more text than an 8-line chunk, so this comparison is confounded by returned text volume, as
the writeup's limitations note; the prediction that dense falls with chunk length is not supported on this shard.
File: benchmark/swebench_lite/SWEBENCH_LITE_retrieval_django.json.

### SWE-bench Lite: equal-text chunk-length analysis (registered 2026-11-14 23:46 MT, before any result)

The django shard showed 400-word chunks raising both retrievers, but six 400-word chunks return far more text than six
8-line chunks. To compare chunk lengths fairly, the 8-line condition is re-scored at a k that returns about the same
number of words as k = 6 with 400-word chunks (k set per task to match the median words returned), for BM25 and dense.
Primary: dense 8-line at equal text vs dense 400-word whole chunk, exact McNemar; prediction, from the writeup, dense
does at least as well with short chunks at equal text. CPU only; it needs a rerun of the retrieval notebooks that
records rankings, launched only on Pupa's go. A null is reported as not detected.

### SWE-bench Lite rerun with gold ranks and the equal-text analysis: implementation (recorded 2026-11-16 15:24 MT, before any result)

Why a rerun: the sympy and scientific-libs shards stopped at Kaggle's 12-hour session limit (39 of 77 and 40 of 61
tasks, about 1,050 seconds per task), the dev-tools-and-web shard never ran, and the equal-text analysis needs rankings
the first run did not record. Code: benchmark/swebench_lite/eqtext_rankings.py. The registered columns are computed by
the same code as before, so on Kaggle the rerun must reproduce the earlier rows; any difference is reported. Known
limit: the 25 percent coverage sample indexes chunks in filesystem walk order, so other machines can draw a different
sample (seen locally on one flask task); Kaggle reruns use the same environment.
Equal text, defined now: W400 is the number of words in the top 6 whole 400-word chunks a retriever returns for a task;
k_eq is the smallest k whose top k 8-line chunks from the same retriever contain at least W400 words (2 local smoke
tasks: 1 to 2 percent more words). Primary: dense 8-line at k_eq vs dense 400-word whole chunks at k = 6, exact
McNemar, two-sided; prediction, from the writeup: short chunks do at least as well at equal text. Secondary: the same
for BM25, and k from the median words per 8-line chunk (the median reading of the earlier wording). Gold ranks are
recorded for every retriever. Holm within the retrieval family of plan amendment 24 (pooled coverage, pooled BM25 vs
dense, equal text). Pooling: benchmark/swebench_lite/pool_swebench_lite.py (no task twice; reproduction check).
Runs: 9 CPU notebooks, task slices sized to stay under 9 hours at the measured rate, with a 10.5-hour save-and-stop
guard: django 1, sympy 3, scientific libraries 3, dev-tools-and-web 2. Launched only on Pupa's go.

### Equal-text analysis: decision rule added (recorded 2026-11-16 19:29 MT, runs in progress, no result seen; Kaggle returns outputs only when a run ends)

Review found that the registered prediction, short chunks do at least as well at equal text, cannot be supported by a
non-significant two-sided McNemar test alone. Added, using the writeup's method (paired bootstrap, 90 percent interval,
margin 0.10, as in its Section 3.3): the paired difference d = hit rate of dense 8-line chunks at k_eq minus hit rate of
dense 400-word whole chunks, with a 90 percent paired bootstrap interval (10,000 resamples of tasks, seed 0). Short
chunks are "at least as good" (non-inferior) if the interval's lower bound is above -0.10; "better" additionally needs
McNemar p below 0.05 after Holm in the retrieval family; "worse" if the upper bound is below 0. Otherwise the result is
inconclusive. The smallest margin the data supports (the negative of the lower bound) is reported. The same is reported
for BM25 as a secondary result. Code: benchmark/swebench_lite/pool_swebench_lite.py.
