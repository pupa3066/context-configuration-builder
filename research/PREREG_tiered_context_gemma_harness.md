# Pre-registration: monolithic vs tiered repository context on the Gemma 4 agent harness

> **Terms used below** (editorial note added 2026-11-14; the registered text is unchanged so its history stays verifiable).
> No-context baseline = C0. Monolithic context, the whole context file in the prompt = C1. Tiered context, an always-on
> index in the prompt with sections loaded on demand = C2. Tiered context with tiers assigned automatically = C3.
> Cost hypothesis, tiered uses fewer tokens than monolithic = H1. Quality hypothesis, tiered resolves no fewer tasks than
> monolithic within a margin (delta) = H2. Tiered resolves no fewer tasks than no context = H3. Automatic tiering matches
> manual tiering = H4.

Recorded 2026-11-14 10:01 MT before any run of conditions C1 or C2 (first design, withdrawn; see Amendment 1). This applies
research/RESEARCH_PLAN.md (design v1, 2026-09-04) to a real multi-step agent with real test grading, the run that
research/STATUS.md lists as missing. It is separate from the Agent Track leaderboard plan and uses no leaderboard slot.

## Question and hypotheses (from RESEARCH_PLAN.md section 2)

- H1 (cost): tiered context (C2) uses fewer total tokens per task than monolithic context (C1).
- H2 (quality, non-inferiority): C2's resolved rate is not worse than C1's by more than delta.
- H3: C2's resolved rate is not worse than no context (C0) by more than delta.
- H4 (automatic tiering, C3) is deferred to a later amendment.

## Conditions (one change each from C0; agent, model, budgets, tools and tasks held constant)

| Cond | Arm | Context |
|---|---|---|
| C0 | benchmark/gemma_agent/submission_v81_noskill | none (official sample prompt) |
| C1 | benchmark/gemma_agent/submission_c1_mono | all four repository context files appended to the system prompt |
| C2 | benchmark/gemma_agent/submission_c2_tiered | an always-on index in the system prompt; each file is a skill loaded on demand with load_skill |

Context content (condition A2): one file per repository, generated by research/c1c2/make_context.py from the
snapshot alone (package layout, each module's first docstring line and top-level public names, test layout, pytest
settings copied from the repository's own config). Commits: fastapi ee22a4b, httpx 4acf5c2, requests 6f205ff, rich
fc41075 (research/c1c2/context/). Same-text control: each file appears verbatim in C1 and in C2's skills
(checked by the build). Deviation noted: the repositories' own contributing docs were too thin for fastapi (33
words) and absent for httpx, so the developer-file condition was replaced by a generated file, ETH's other
condition. Model: gemma-4-31b-it-qat-w4a16-ct; tasks: all 129 published tasks; budgets: eval_config.yaml of C0.

## Mechanism gate (checked in traces before any outcome is analysed)

C1: the system instruction in each trace contains all four context files. C2: in at least 80 percent of tasks a
load_skill call names the skill of the task's repository. If a gate fails, the condition is reported as not
implemented and its outcomes are not used for H1 to H3.

## Outcomes and statistics (RESEARCH_PLAN.md section 6)

- Tokens: total_prompt_tokens plus total_completion_tokens per task (trace final_metrics). H1: paired Wilcoxon
  signed-rank, C2 vs C1, one-sided.
- Resolution: H2 and H3 by a paired bootstrap (10,000 resamples) one-sided 95 percent lower bound of the
  difference in resolved rate (C2 minus C1, C2 minus C0) compared with minus delta; exact McNemar reported.
- delta = 0.05 (5 points). Deviation from the plan's 2 points, declared: with the measured discordance of 8 in 129
  paired tasks, 2 points needs about 960 paired runs; one run of 129 detects about 5.4 points at 80 percent power,
  three runs about 3.1 points. Achieved power is reported.
- alpha = 0.05, Holm correction across H1, H2, H3. Effect sizes with intervals and a resolved-rate versus tokens
  (Pareto) plot are reported.
- Repeats: k = 3. Run 1 now (C1 and C2 fresh; C0 from the existing 129-task run of the same arm and harness,
  benchmark/gemma_agent/selftest_results/selftest129_v81_noskill.csv, declared). Runs 2 and 3 after the GPU
  quota resets of 2026-11-21 and 2026-11-28, with fresh C0, C1 and C2. Results stay labelled preliminary until
  all three runs are in; nulls are reported as not detected.

## Amendment 1 (recorded 2026-11-14 11:27 MT, before any outcome of a valid run)

Withdrawn first design (runs launched 10:02 MT). Review found two validity problems before results: (1) C1 put all
four repositories' files in every prompt, so C2 saved tokens only by omitting other repositories' files, a routing
effect rather than tiering; ETH's monolithic condition is the context file of the repository being worked on.
(2) C2 loaded whole files and its prompt forced a first load_skill call that C1 lacked. The C1 run was stopped. The
C2 run completed with 0 tool calls on all 129 tasks: each SKILL.md description contained an unquoted ": ", the
harness rejected the frontmatter as invalid YAML, and the agent never compiled. Neither run is used.
Validator change: skill frontmatter is now parsed with yaml.safe_load, as the harness does
(benchmark/gemma_agent/validate_submission.py); it rejects the withdrawn arm and passes all current arms.

Corrected design, replacing the conditions table above:
- Per-repository arms, routed by task: each task runs with its own repository's arm.
  C1 = benchmark/gemma_agent/context_study/monolithic/<repo>: that repository's whole file in the system prompt.
  C2 = benchmark/gemma_agent/context_study/tiered/<repo>: the always-on part (header, tests, documentation
  examples, and an index of the package-layout sections) in the system prompt; each layout section, grouped by
  directory, is a skill loaded on demand. Sections per repository: fastapi 6, httpx 2, rich 2, requests 1.
- Built by research/tiered_context_gemma/build_arms.py from the files of research/tiered_context_gemma/make_context.py.
  Same-text control (asserted by the build): always-on part plus all sections equal the C1 file exactly; the index
  is the only added text. Both prompts open with the same sentence; C2 adds one sentence saying sections are loaded
  with load_skill when needed. No forced first call.
- H1 primary measure, as in RESEARCH_PLAN.md: prompt tokens per model call (total_prompt_tokens divided by
  model calls, per task), C2 vs C1, paired Wilcoxon, one-sided. Secondary: total tokens per task.
- Mechanism gate: C1 traces contain the whole file; C2 traces contain the always-on part, and the share of tasks
  with at least one load_skill call is reported (no threshold: loading on demand may legitimately be rare).
- H2, H3, delta, alpha, Holm, repeats and labelling as registered above. Run 1: C1 and C2 fresh on 129 tasks; C0
  from the existing 129-task run, as declared.
